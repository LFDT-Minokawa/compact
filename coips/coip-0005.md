## Abstract

Compact currently supports a single ledger (in reality zkir and onchain-runtime)
version. However, the instance has arised that different networks are using
different versions of ledger at a single point in time. E.g., mainnet uses
ledger-8.0 whereas preview has moved on to ledger-9.1.

Currently, this either requires maintaining multiple versions of Compact in parallel
or Compact has to support several ledgers at once. This CoIP advocates for the latter.

## Motivation

A single version of Compact currently supports a single version of ledger, resulting
in supporting a single network.
This limitation significantly increases effort in releasing (currently, Compact
uses a single release channel) and maintaining
multiple versions of Compact as multiple networks use different versions of
the ledger. Consequently, it transfers the burden of choosing the correct version
of Compact for each network onto the user.

## Specification

The design starts from the user experience of the developer tool; the
compiler's interface follows from it.

A user compiles for a *network*. The developer tool defaults to `mainnet`:

```
compact compile <input.compact> <output-dir>                    # mainnet
compact --network=preview compile <input.compact> <output-dir>
```

The compiler itself does not know about networks. What Compact depends on
directly are the **on-chain runtime** and **ZKIR**, and a given `compactc` is
built for one pair of them. The developer tool resolves a network to that pair
through the compatibility matrix and invokes the matching build.

The two are independent as *concepts* — separate components, separately
versioned, and used in different parts of the compiler. They
are nonetheless not freely combinable, for two reasons. At the moment 
(they will be separated soon), they ship together, so
the pairs that exist are the pairs some ledger release produced.
And some combinations are known not to work at all: a ledger version relies
on a version of midnight-zk which provides the proof system for ZKIR, similarly,
a ledger versions relies on reperesentation from onchain-runtime.

That is why they are bound into one thing rather than offered as two orthogonal
switches. Treating them as independent would imply every pair is buildable,
which is false; treating them as a single version number would hide that they
are separate dependencies that move at different rates. The supported
combinations are therefore an enumerated, finite set, and the rest of this
document calls one such combination a *target* — the same shape as a machine
type naming an operating system and an architecture together. 

A target is deprecated once there is no network using a version of the
ledger that relies on that target. Similarly a new target is added when
the Minokawa TSC has approved a request that a network needs to support
a new target. When a network is scheduled to migrate from target `x` to `y`
there will be a period of time to keep target `x` under Compact. If no other
network relies on target `x`, once the period is passed target `x` will be
deprecated from Compact.

A release ships one `compactc` build per target rather than one binary that
selects a target at run time; the developer tool picks the build.

## Rationale

This rationale does not consider the interaction of `--feature-zkir-v3` with
targets since it will be deprecated soon. If in the future, there is a need
to support multiple versions of zkir in a single target, a flag can be added.
For now, that concern is out-of-scope for this CoIP.

### Developer tool

The Compact developer tool is the recommended way for users to
interact with Compact. It
surfaces the *network* through a `--network=<some-network>` flag, **defaulting to
`mainnet`**, and resolves that network to the on-chain runtime and ZKIR versions
the compiler needs through a compatibility matrix it maintains:

| network | ledger | on-chain runtime | ZKIR |
| ------- | ------ | ---------------- | ---- |
| mainnet | 8.0    | 3.0              | 3.0  |
| preprod | 9.1    | 4.0              | 3.1  |
| preview | 10.0   | 5.0              | 3.1  |

The ledger column is what the networks are described by and what decides
the deprecation or addition of a target.
The last two columns are what the compiler is actually built with.

A target can be targeted by multiple networks but a network cannot target
multiple targets.

For example, `compact compile ...` with no network flag compiles for `mainnet`,
and `compact --network=preview compile ...` looks up preview's on-chain runtime
and ZKIR versions and invokes the compiler built for them. It then looks up the
registery of the compilers and looks for the artifact name that matches the
requested architecture and target. The compiler artifacts
include the target as well as the architecture: as of writing this proposal
the artifact names are `compactc_v<version>_<arch>.zip`. With this change,
the names will become `compactc_v<version>_<arch>_<target>.zip`, for instance,
`compactc_v0.36.0_aarch64-darwin_ocrt3.0-zkir3.0.zip`.

This design modulates what the user needs to know: the average user does not
need to know which on-chain runtime or ZKIR the network they are deploying to
runs. A user who wants a specific target invokes that target's `compactc`
build directly.

The devtool's only job here is to resolve the
network to a target and select the matching build, and to fail clearly when the
installed release does not contain a matching build for the requested network.
For example, assuming that the first release that supports this proposal is
`compactc 0.36.0`:

```
> compact update 0.31.1
> compact --network=preview compile some-contract.compact some-output-dir
error: `--network` is only supported for Compact 0.36.0 onward
       use `compact list` to see a list of available Compact compiler
> compact update 0.36.0
compact: aarch64-darwin -- network=mainnet -- ocrt3.0-zkir3.0 -- 0.36.0 -- default.
compact: aarch64-darwin -- network=preprod -- ocrt4.0-zkir3.1 -- 0.36.0 -- installed.
compact: aarch64-darwin -- network=preview -- ocrt5.0-zkir3.1 -- 0.36.0 -- installed.
> compact --network=preview compile some-contract.compact some-output-dir
```

Whereas 

```
> compact update 0.36.0 --network=mainnet
compact: aarch64-darwin -- network=mainnet -- ocrt3.0-zkir3.0 -- 0.36.0 -- default.
compact: aarch64-darwin -- network=preprod -- ocrt4.0-zkir3.1 -- 0.36.0 -- uninstalled.
compact: aarch64-darwin -- network=preview -- ocrt5.0-zkir3.1 -- 0.36.0 -- uninstalled.
> compact --network=preview compile some-contract.compact some-output-dir
error: you do not have a compatible compiler installed
       run `compact list --network=preview` to get a list compatible compilers
```

### Compiler

A handful of compiler passes and data files depend on the on-chain runtime and
ZKIR. These can be duplicated in a subdirectory per supported target. The
files/subdirectories are:

- `compiler/typescript-passes.ss` and `compiler/typescript-passes`
- `compiler/zkir-passes.ss` and `compiler/zkir-passes`
- `compiler/standard-library.compact`
- `compiler/midnight-ledger.ss`
- `compiler/midnight-natives.ss`

A target is identified by
`ocrt-<version>-zkir-<version>` — for instance `ocrt-3_0-zkir-3_0`, which
describes what the compiler builds on mainnet today.

These files move to `compiler/targets/<target>/`, one directory per supported
target. A target directory lives as long as some network needs it, that is, once
every network has been promoted off it — not simultaneously, and over a span of
weeks to months — the directory is dropped after a grace period.
Similarly, a target directory is
created when the Minokawa TSC has received and approved a request for it, with a
timeline of when a network will be promoted to it.

The compiler is not concerned with which network runs which ledger, and it
should not be configured by ledger version at all. The ledger is not a direct
dependency of the compiler; it only tells us indirectly which on-chain runtime.

The requirement of the compiler must never silently pick a target is
satisfied structurally: a `compactc` build *is* one
target, so there is no selection to make and nothing to retarget when a
component is deprecated. `compactc --target` reports which build you are
holding and it cannot be asked for another:

```
$ compactc --target
onchain-runtime=3.0, zkir=3.0
```

A caller that needs to be sure it invoked the right build — a script with a
hardcoded path, or CI — asks first and compares, rather than passing an
assertion for the compiler to check. After the fact the artifact needs to be
self-describing too, thus, `contract-manifest.json` records the target pair
as well.

`ledger.ss` and `natives.ss` should not be target-dependent — they are macro
machinery — while `midnight-ledger.ss` and `midnight-natives.ss`, the data they
include, are. So the include of `midnight-ledger` and `midnight-natives` in
`ledger.ss` and `natives.ss` respectively resolves according to the selected
target. This is a deliberate choice over duplicating those two files, which
would copy roughly 450 lines of machinery that is not target-dependent. If the
evolution of these macro machineries diverge significantly from one target to
another, a potential design is to include the target version in the macro
machinery. However, that is not the case as of writing this proposal.

The standard library is **target-dependent**. Adding a native to the standard
library requires a JavaScript implementation of that native in the Compact
runtime, which may require on-chain runtime support, and a ZKIR implementation,
which may require new ZKIR gates; `verifyProof` and the `secp256k1` circuits are
the worked examples. The existing `compiler/zkir-v3-library.compact` is the
visible consequence of this today — it holds standard library circuits and types
that are not available under ZKIR v2.

### Runtime

The Compact runtime relies only on the on-chain runtime, which for now is shipped as
part of a ledger release. `runtime/package.json` pins the 
`@midnight-ntwrk/onchain-runtime-v3` for `compact-runtime 0.16.0` and
`@midnightntwrk/onchain-runtime-v<number>` for `compact-runtime 0.18.0` onward.
Runtime directories
are therefore keyed on the **on-chain runtime version** rather than on a full
target — `compact/runtime/ocrt-4_0/` and so on — with one directory per
supported on-chain runtime instead of one per target. If the ZKIR WASM is later
imported into the Compact runtime the runtime acquires the
second axis too and these become full targets.

For simplicity, a single version of Compact runtime should not support multiple
on-chain runtime versions. For example `compact-runtime 0.16.0` supports one and
`compact-runtime 0.19.0` another, and this will be the ongoing convention.
Compact runtime is published on npm. With a single release of the Compact
compiler covering several targets, the internal runtime subdirectory needs to be
duplicated per on-chain runtime as well. Creating and deprecating these
directories follows the same rule as the compiler's target directories. The difference is that
the runtime does not need to refactor the parts of the runtime that are shared and
the parts that rely on onchain runtime. The trade off here is simplicity at the cost
of duplication. `flake.nix` needs to be updated to build the runtime for each
Compact runtime.

## Backwards Compatibility

For users of the developer tool this is **not** a breaking change. `compact
compile` with no network flag keeps working and compiles for `mainnet`. However,
once this proposal is implemented and shipped, deprecating a target becomes
a **breaking change**.

For users invoking `compactc` directly it is also **not** a breaking change: 
the user has to manually install the compiler binary that matches their desired
compiler targets and compile their contracts. However, for CI and scripts that
rely on the name of the artifact, this **is** a breaking change since the artifact
names will include the targets within them.

## Security Implications

If a security vulnerability is found in passes that are duplicated, the fix must
be applied to all currently supported targets, making Compact more vulnerable.

A CI check is required to diff the target-independent files across the runtime
directories. It must fail on unexplained divergence. This turns "a fix must be
applied to all supported runtimes" from a thing maintainers must remember into a
thing CI enforces. The compiler is out-of-scope for the drift check.

## How to Teach This

`compact compile <input.compact> <output-dir>`
keeps working and compiles for `mainnet`. A user who wants a different network
adds one flag:

```
compact --network=preview compile <input.compact> <output-dir>
```

Users who invoke `compactc` directly must now explicitly install and run the compiler
binary built for their desired target.

## Implementation

**Phase 0 - compiler restructure, no behavioral change: introduce the target directory, one target, add --target flag.**

*Acceptance criteria:* `nix build` builds successfully for the single target, 
`nix develop` starts a nix shell successfully for the single target, and
`compiler/go` passes for the used target with the same coverage. All CI pass, test is added for
`contract-manifest.json` recording onchain-runtime and zkir versions of the
target. `compactc --target` prints the single target. Documentation reveals
the dependency either in terms of the network or the target. Accordingly,
the workflows for syncing docs work.

**Phase 1: runtime restructure, one runtime.**

*Acceptance criteria:* `nix build .#runtime-ocrt-<version>` is green and the
published tarball is identical to the pre-move tarball except for paths. The
`checkPhase` of `packages.compactc` passes against the relocated
`node_modules`, and the runtime's own suite passes. Documentation lands at the
new path and `check-docs-sync.yml` is green. The drift check passes with one
runtime and one target **and has been shown to fail** on a deliberately injected
divergence — it has nothing to compare against until phase 2, so a check that
has never failed is not known to work.

**Phase 2: add the second target coming from ledger-8 branch.**

*Acceptance criteria:* the build matrix is green for both targets.
`compactc --target` reports the right pair from each build, and two builds of
the same contract from different targets differ in the expected places and
nowhere else. The mismatched-runtime test fails inside `checkRuntimeVersion`
with the version-mismatch message. The target-switching test passes, and fails
if the per-target object directories are reverted. The drift check is now
comparing two real targets and two real runtimes.

**Phase 3: developer tool and release workflows.**

*Acceptance criteria:* `compact compile` with no flag resolves to `mainnet` and
invokes that target's build; `--network` resolves correctly for every network in
the matrix, asserting on **which build was invoked** and reading the expected
target from the matrix rather than hardcoding it, so the tests do not go stale
when a network is promoted. The three error paths match golden files. A user
with one network installed has exactly one `compactc` on disk. The e2e suite is
green per network using the ledger the matrix resolves to.

## Rejected Ideas

### Multiple release branches

Compact could potentially use a branch per network for its releases. 
However, this approach still puts the burden of choosing the correct version
of Compact on the user. Furthermore, it is burdonsome to maintain and release.
Consider a patch release for a bug. The Compact maintainers must then cut three
releases. 

### A Compact runtime that supports multiple ledgers

Complicated and requires lots of refactoring and design effort.

### A single build of Compact compiler using a `--ledger` flag

Two separate ideas were rejected here:

**The `--ledger` flag** was rejected because it is not granular enough to
capture the actual dependencies of the compiler, which at the time of writing
are the on-chain runtime and ZKIR. The ledger only indirectly constrains which
of those may be used; configuring the compiler by it means naming something the
compiler does not depend on.

**A single build selecting a target at run time** was rejected because it moves
target variation inside the compiler, where every maintainer pays for it on
every task rather than only when adding or dropping a target. It adds complication
to compiler development at the cost of shipping a single artifact per architecture.

What this costs us is worth stating. A single build would have shipped one
artifact rather than several, would have been able to answer "what do you
support?" from the binary itself rather than from a release manifest, and would
have let one `compiler/go` run exercise every target locally. That last point is
the real loss: under the chosen design a local run covers the target you built,
and cross-target breakage surfaces in CI instead. This is judged acceptable
because roughly 75% of the compiler source is target-independent, so for most
work a single-target local run is both faster and complete.

### Building `compactc` on the user's machine

Instead of shipping one `compactc` per target, the release could ship one per
platform together with the compiler sources, and have the developer tool run a
configuration-and-build step the first time a network is requested. This was
rejected.

It would change what a user installs. Today's `compactc` is standalone —
`chez-exe` produces an executable that needs no Chez on
the user's machine. Building one locally instead requires shipping and
installing Chez Scheme and `chez-exe`, and the roughly 29,000 lines of compiler source, then
running a `compile-whole-program` over all of it. A contract developer would be
installing a Scheme toolchain to compile a contract, and would pay a full
compiler build the first time they targeted a new network. How long that build
takes has not been measured; it would need to be before this could be
reconsidered.

It would also weaken the release rather than strengthen it. The published
artifact would no longer be what runs, so a compiler version would become a
recipe rather than a thing that can be hashed, attested, or reproduced — a
meaningful loss for a compiler that emits on-chain code — and "works on my
machine" would become possible for the compiler itself and not only for
contracts.

Finally, it saves less than it appears to. CI still has to build every
(target, platform) pair in order to test them, so the work is moved onto users
rather than avoided, and the artifact is given up in exchange.

The problem it was meant to solve — a release carrying N times as many binaries
— is better addressed by the fetch model already in the developer tool, which
downloads one build rather than the release.

## Open questions

Some of the proposed design decisions thus far in the proposal are questioned.
The answer to such questions supersedes the design proposed above.

- Can `format` and `fixup` become target-dependent?
  They track the *language* version, not the ledger. The formatter needs a
  separate implementation only when the language makes a breaking change 
  (the `assert` syntax change is the example), and fixups are compiled into the
  tool rather than parameterised over. Whether these should become independently
  versioned tools with their own release cadence was raised and is **out of 
  scope for this CoIP**.
- Is there a timeline for promotion of networks? 
  This helps decide the maintenance burden of multiple target and runtime
  subdirectories. The stated goal is a Cardano-like model — mainnet, pre-prod
  giving early access to a coming mainnet upgrade, and preview giving early
  access to new features, with regular promotion between them — but we are not
  there yet, so no cadence can be reliedon.
- Should the standard library be versioned?
  If changes stay additive, a single set of documentation could say "this
  feature requires at least ZKIR 3.2 and on-chain runtime 4.7". Breaking changes
  make that harder. Versioning the standard library is postponed until we reach Compact 1.0.
- How does a user develop their own local network that we do not know about
  select a target? 
  If the target is already suppported by the compiler the 
  network needs to be added to the devtool. If the target is not supported 
  by the compiler a local development and build of the compiler is needed
  in addition to adding support to the devtool. **A nice-to-have mechanism.**
- Should the split be proactive — treating every file that *could* become
  on-chain-runtime or ZKIR dependent as target-specific from the start — or
  reactive, splitting each file when it actually diverges? This CoIP is taking
  a mainly proactive approach except for `compiler/field.ss`, `compiler/natives.ss`,
  `compiler/ledger.ss`, `compiler/midnight-inlines.ss`, `compiler/midnight-events.ss`,
  `compiler/inlines.ss`, and `compiler/events.ss`. The target could also be
  encoded in the macros used in `midnight-*.ss` instead of splitting the files
  in target subdirectories. 
- What are the implications on downstream components like compact.js, midnight.js? 
  From initial discussions, one would expect the downstream components to adopt the same design
  of supporting multiple ledgers, otherwise, the benefit added is only when a user
  is compiling a contract.
- How should the documentation (ledger ADT and standard library) handle versions?
  Should they reveal both the network and target?
- Let's make a decision on supporting a single zkir version for a target or 
  multiple. This could potentially result in supporting multiple targets per
  network. Override `--network=...` with `--targt=...` in devtool?
- Will `onchain-runtime` always be released with a suffix of its major version?
- Does the ledger team perceive a change in `max-field` allowed in the future?
  If so, `compiler/field.ss` also becomes target-dependent. 
- Should the compiler (or the devtool) accept a node RPC endpoint and derive the
  target from the network it points at?
